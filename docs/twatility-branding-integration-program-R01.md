# TWAtility Belt branding integration program R01

## Decision and authority

This document is the agreed execution plan for applying the presentation and
selected structural improvements demonstrated by `ui-mock/` to the production
Chrome extension.

The work is a controlled UI migration, not a replacement of the extension with
the click-through mock. The mock is design evidence. The latest `master` branch,
its active feature contracts, its current program documents, and its production
behaviour remain authoritative for functionality.

Authority is applied in this order:

1. current user direction;
2. `docs/swarmforge-active-scope.md` and the active contracts and programs named
   by it from the latest `origin/master`;
3. this branding integration program;
4. the committed `ui-mock/` reference;
5. existing styling and presentation where none of the above gives a direction.

The integration agent must reread the current `origin/master` version of
`docs/swarmforge-active-scope.md` before making an ancestry, scope, behaviour, or
verification decision. Ongoing work on `master` may make production more complete
than the mock. The agent must compare current implementations rather than assume
the mock should win.

## Objective

Deliver a merge-ready non-`master` branch containing a production-quality
TWAtility Belt redesign of the real extension while preserving every supported
control, state transition, persistence effect, recovery route, keyboard path,
focus contract, and Chrome API side effect.

The finished branch shall:

- carry the restrained British-comic visual language approved in the mock;
- use the TWAtility Belt wordmark and genuine-alpha artwork appropriately;
- retain realistic production data and all production functionality;
- adopt structural improvements only where they improve the real interaction
  without reducing its semantics;
- remain usable at modern side-panel and desktop Studio sizes;
- avoid unnecessary whole-page horizontal scrolling;
- be synchronized with the newest available `origin/master`;
- pass the proportional slice checks and final full verification described here;
- contain reviewable, bounded commits on non-`master` branches; and
- be pushed for final human review without directly updating `master`.

## Branch and worktree procedure

### Protect the agreed reference

In the existing `feature/ui-mock` worktree:

1. verify the branch and inspect all changes;
2. commit this program document by itself with a documentation commit;
3. commit only `ui-mock/` in a second atomic design-reference commit;
4. confirm no unrelated files entered either commit;
5. push `feature/ui-mock` and configure its upstream; and
6. record both commit hashes in the first branding handover report.

The separate document commit is intentional. It can be cherry-picked into the
production branding branch without importing the mock.

### Create the implementation line

1. inspect configured remotes and fetch the latest remote state;
2. create a sibling worktree containing a new
   `feature/twatility-branding` branch from the newest `origin/master`;
3. cherry-pick only the isolated program-document commit;
4. keep the original worktree on the frozen `feature/ui-mock` branch for visual
   comparison;
5. verify that the branding worktree is clean and that `ui-mock/` has not entered
   the production branch; and
6. push `feature/twatility-branding` and configure its upstream after the first
   integration commit.

The agent must ensure both worktrees are available to the execution environment.
If the runtime restricts sibling paths, it may create a temporary exported copy of
the committed mock inside an approved temporary directory. That copy must not be
committed to the production branch.

### Work in bounded slices

For each implementation slice:

1. fetch the remote;
2. record the previous and newly fetched master base commits;
3. diff those master bases and inventory every added or changed control, state,
   route, persistence contract, active-scope requirement, and verification owner;
4. update and classify the parity matrix for that upstream delta before changing
   production presentation;
5. merge the newly fetched `origin/master` into the shared branding integration
   branch;
6. reread current active-scope authority;
7. run the slice's cheap baseline checks;
8. create a short-lived slice branch from the integration branch;
9. implement only the approved slice;
10. keep presentation, structural behaviour, tests, and generated output in
   separable commits where practical;
11. run the slice verification gate;
12. visually inspect the real extension, not only the mock;
13. merge the slice into `feature/twatility-branding` without rewriting shared
    history;
14. fetch master again if it moved during the slice;
15. record, diff, and classify that second master delta;
16. merge the updated `origin/master` into the branding integration branch;
17. rerun checks for overlapping or behaviourally affected areas;
18. push the integration and slice branches; and
19. provide the user with the defined slice review bundle.

Do not continuously merge every upstream commit while editing. Synchronize at
slice boundaries so conflicts are handled in coherent batches.

The master-delta parity step is mandatory even when the merge is clean. New
upstream functionality must be absorbed into the preservation contract rather than
silently falling outside the original mock crosswalk.

## Feature-preservation contract

The redesign may regroup controls; it must not thin them out.

For every production control family, the integration must retain:

- the action itself;
- its enabled, disabled, hidden, loading, success, error, empty, and recovery
  states where applicable;
- the truthful reason an action is unavailable;
- the same real state and persistence boundary;
- all import, export, clipboard, file, storage, Chrome API, command, and navigation
  effects;
- stable identities and reference semantics;
- Undo, Redo, revision, publication, and conflict behaviour;
- keyboard operation and focus restoration;
- accessible names, descriptions, roles, relationships, announcements, and error
  association;
- destructive-action review and dependency impact;
- responsive access to the control; and
- a visible recovery path when the production extension currently provides one.

Existing IDs, `data-*` hooks, `aria-*` relationships, action labels queried by
tests, and `hidden` state ownership must be preserved unless an approved structural
change updates all production wiring and evidence together.

The mock's hardcoded data, fake persistence, predetermined toasts, and presentation
JavaScript must never replace production state or effects.

## Required parity audit

Slice 0 is read-only with respect to production behaviour. Its primary deliverable
is `docs/twatility-branding-parity-matrix-R01.md`.

Each row must contain:

| Column | Required content |
| --- | --- |
| Surface or workflow | Human-readable scope |
| Production owner | HTML, CSS, renderer, state, and persistence files |
| Production controls | IDs, roles, commands, conditional actions, and states |
| Mock destination | Corresponding mock page, section, or state |
| Classification | One of the five classifications below |
| Preserve contract | Behaviour that cannot change |
| Proposed migration | Exact presentation or structural change |
| Risk tier | V0, V1, V2, or V3 |
| Verification | Exact automated and manual checks |
| Master collision risk | Files or active work likely to overlap |
| Decision and status | Approved, preserve, revise, omit, in progress, or complete |

Every area must receive one primary classification:

1. **Structural improvement** — production structure should change because the
   mock or another current production seam presents the real task more clearly.
2. **Branding/layout parity** — existing real controls are regrouped or wrapped,
   while behaviour and state ownership remain unchanged.
3. **Brush-on styling** — tokens, typography, colour, borders, spacing, shadows,
   badges, focus rings, responsive rules, or decorative artwork can be applied
   without structural change.
4. **Preserve implementation** — current production is semantically stronger or
   more complete; the mock may influence styling but not the interaction model.
5. **Mock-only / do not port** — tour content, hardcoded examples, fake feedback,
   illustrative counts, or interactions that have no supported production
   equivalent.

The matrix must cover all rows in `ui-mock/control-map.html`, the rare states in
`ui-mock/state-gallery.html`, all production side-panel workspaces and Data Layer
views, the complete Studio collection tree and inspector, all dialogs, and all
conditional or recovery actions.

The agent shall present the completed classification to the user before broad
production implementation. This is a review gate, not a terminal deliverable. Once
agreed, the agent continues through every slice.

## Implementation architecture

### Prefer additive, scoped presentation foundations

To reduce conflicts with ongoing master work:

- add a shared local branding/token stylesheet;
- add small surface-specific branding stylesheets for the side panel and Studio;
- load them after the existing functional stylesheets;
- scope the redesign beneath an explicit TWAtility theme class;
- avoid wholesale formatting or rewriting of the large existing HTML and CSS
  files;
- use semantic component classes rather than brittle positional selectors; and
- consolidate existing CSS only after the redesign is stable and verified.

A suitable starting structure is:

- `twatility-brand.css`;
- `side-panel-brand.css`;
- `specification-builder-brand.css`; and
- `assets/brand/`.

Names may change after inspecting current master, but the separation of shared
tokens, surface-specific presentation, and production behaviour should remain.

### Packaging

The foundation slice must:

- teach `scripts/build.mjs` and the packaging flow to copy every required local
  branding asset and stylesheet;
- ensure `specification-builder-guidance.css` is present in `dist/` if it remains
  referenced;
- keep all extension assets local and compatible with the extension content
  security policy;
- use genuine-alpha PNGs wherever bitmap artwork overlays a UI surface;
- avoid remote fonts and images;
- verify built HTML references only files present in `dist/`; and
- load and inspect the built extension rather than relying only on source pages.

The CSS wordmark should remain code-native and scalable. The mascot and utility
belt may use the approved transparent assets. Decorative artwork must not obscure,
replace, or imply unavailable functionality. Projects must not acquire fictional
logos.

### Rule and condition builder

The mock's rule presentation is inspiration, not implementation markup.

Production already has or is expected to have a shared nested condition renderer
supporting stable identities, typed property/operator/value controls, nested
All/Any/Not groups, and Not's single-child invariant. Current active scope also
requires the condition builder to begin with **Add condition** and **Add group**.

The structural rule slice must:

- use the shared production condition-tree semantics;
- apply the clearer progressive disclosure and row hierarchy demonstrated by the
  approved design;
- remove or consolidate any older flattened Studio representation that cannot
  round-trip nested groups;
- preserve rule Then outcomes and optional When trees;
- preserve typed values, stable identity, focus restoration, persistence, and
  Undo;
- keep every control inside the viewport at 360 CSS pixels;
- minimally scroll growing nested layers into complete view;
- prove render, edit, save, reload, inherited update, sparse override, reset, and
  Undo behaviour; and
- keep structural changes separate from visual styling commits.

The agent must not replace a stronger production builder with the simpler static
mock representation.

## Verification strategy

Verification is proportional to behavioural risk. Passing screenshots never
substitutes for functional evidence, and blanket suites are not repeated after
every cosmetic edit.

### Risk tiers

**V0 — brush-on presentation**

Examples: tokens, colour, borders, shadows, spacing, typography, decorative
backgrounds.

Required:

- one build;
- relevant lightweight browser smoke;
- console, page-error, failed-request, and overflow inspection;
- screenshots at the applicable canonical widths; and
- keyboard focus visibility on touched controls.

**V1 — branding/layout parity**

Examples: wrappers, cards, regrouped existing actions, responsive reflow, dialog
layout.

Required:

- V0 checks;
- control-ID and accessible-relationship equivalence;
- action hierarchy and tab/keyboard checks;
- dialog open, cancel, confirm, and focus-return checks; and
- state variants for the touched surface.

**V2 — structural renderer change**

Examples: condition builder, project-card renderer, inspector mounting, dynamic
form composition.

Required:

- V1 checks;
- exact unit tests for the touched model and renderer;
- applicable property tests;
- applicable browser adapter;
- persistence or serialization round-trip checks;
- state-transition and Undo evidence; and
- the relevant focused verification pack once at slice completion.

**V3 — integration boundary**

Examples: master synchronization that overlaps touched code, final branch
integration, packaging.

Required:

- rebuild from source;
- tests for every overlapping pack;
- source-based resolution followed by regenerated `dist/`;
- packaged-extension loading; and
- the final full gate when specified below.

### Baseline and slice cadence

- Establish a current-master targeted baseline in Slice 0.
- Prefer current upstream CI evidence to rerunning a full baseline that will become
  stale immediately.
- During a slice, run the cheapest relevant checks after meaningful changes.
- At the slice boundary, run the complete affected tests and one relevant focused
  pack where required by risk or current active scope.
- After a master merge, rerun only packs that overlap or depend on the merged
  changes unless current authority requires more.
- Do not run `npm test` after every slice.

### Final gate

Immediately before the final gate:

1. fetch `origin/master`;
2. record the observed commit hash and UTC timestamp as `FINAL_MASTER_BASE`;
3. perform the mandatory master-delta inventory and parity update from the
   previously recorded master base to `FINAL_MASTER_BASE`;
4. merge `FINAL_MASTER_BASE` into `feature/twatility-branding`; and
5. resolve source conflicts and regenerate build output.

That recorded commit is the finite integration cutoff. Commits arriving on master
after the cutoff are listed in the final report as post-cutoff work; they do not
create an endless requirement to restart the completed gate. A later merge attempt
can validate those commits proportionally as a new integration delta.

Against `FINAL_MASTER_BASE`:

1. run `npm test` once;
2. run `npm run package`;
3. load the packaged `dist/` extension in a controlled Chrome profile;
4. inspect all side-panel workspaces and Studio routes;
5. verify control equivalence against the final parity matrix;
6. exercise representative create, edit, save, undo, import, export, recovery,
   condition, project, and cross-window flows;
7. complete keyboard, focus, zoom, contrast, reduced-motion, forced-colours,
   responsive, overflow, console, page-error, and failed-request checks;
8. commit the verified final `dist/` output;
9. push the final integration branch; and
10. report exact baseline, head, `FINAL_MASTER_BASE`, cutoff timestamp, post-cutoff
   master commits if any, tests, package, and review evidence.

Known pre-existing failures must be demonstrated on the latest master baseline and
reported separately. New failures, lost controls, or weakened semantics block
completion.

## Visual review sizes

At minimum:

- side panel: 360 × 760, 420 × 900, and 512 × 900 CSS pixels;
- Studio: 1280 × 900, 1440 × 900, and 1720 × 960 CSS pixels; and
- applicable zoom checks at 200%.

At each size inspect:

- whole-page horizontal overflow;
- local horizontal scrollers;
- clipped actions;
- overlapping text, JSON, code, labels, toolbars, or dialogs;
- focus visibility;
- heading and action hierarchy;
- transparent-artwork edges;
- status and disabled contrast;
- sticky-region collisions; and
- access to every production control.

## Stop and escalation conditions

The agent should make ordinary implementation decisions autonomously. It must
pause and ask the user only when:

- the mock and current active behaviour require materially incompatible product
  choices;
- preserving a production function would require a visibly different design and
  the parity matrix has no agreed decision;
- completing the work requires committing or pushing directly to `master`;
- remote credentials, branch protection, or environment permissions prevent the
  authorized non-master workflow;
- a destructive repository operation would be required;
- an existing uncommitted user change overlaps the slice and cannot be preserved;
  or
- a new failure indicates a genuine behavioural contract change rather than a UI
  regression.

Difficulty, test duration, merge conflicts, or the amount of remaining work are
not completion or escalation conditions.

## Terminal definition of done

This program is complete only when:

- the approved mock is safely committed and pushed on `feature/ui-mock`;
- the plan and final parity matrix are committed on
  `feature/twatility-branding`;

The agent must not mark the goal complete after planning, auditing, creating the
theme foundation, or finishing only one surface.
